# IR-286: can Kani prove through `exact::expression`'s `Frame::call`?

Spike, not a SpecReview: no quire-validated artifact, no coverage claim. Kani
0.67.0 (cargo plugin), CBMC via `cargo kani`, run on this machine (20 cores,
62 GiB RAM) from a worktree at `origin/main` `c52442a`.

## What was built

`verification/kani_spike_ir286.rs`, wired into `src/lib.rs` as its own
`#[cfg(kani)]` module (`kani_spike_ir286`), kept separate from
`verification/kani.rs` so `scripts/check_kani_harnesses.py`'s declared
8-harness census is untouched (`python3 scripts/check_kani_harnesses.py`
still reports 8 after this change). Neither proof here is wired into
`make kani`.

Three harnesses:

- `ir286_frame_call_add_one_bounded` — the ticket's ask: declares a
  one-function package `f(x: Int[0,9]) = x + 1` through the real
  `PackageDeclarations` -> `check` -> `CheckedPackage` -> `check_expression`
  -> `evaluate` -> `Frame::call` path, `x` symbolic (`kani::any::<i64>()`,
  `kani::assume` to `0..=9`), body running the real
  `evaluate_integer_arithmetic(IntegerArithmetic::Add(x, 1), None, meter)`
  over real `exact::Integer` (`num_bigint::BigInt`) values, asserting the
  result is in `[1,10]`.
- `ir286_frame_call_add_one_bounded_mutated` — same call surface, asserting
  the result is `<= 9` instead (false for `x=9`, where `f(9)=10`): the
  sabotage/mutation witness that should report a CBMC counterexample.
- `ir286_package_check_and_drop_only` — added mid-spike as a diagnostic, not
  one of the two the ticket asked for. No symbolic input, no `Frame::call`,
  no arithmetic: just `add_one_package().check(...)`, then drop. Isolates
  whether the blowup needs arithmetic/calls at all.

## Method

Each run: `timeout <cap> systemd-run --user --scope -p MemoryMax=12G cargo
kani --features exact --harness <name> [--exact]`, wrapped in `/usr/bin/time
-v`. `CARGO_TARGET_DIR` pointed at the worktree's own `target/`.

Caveat on the memory numbers below: `/usr/bin/time -v`'s "Maximum resident
set size" measures the process it launches directly
(`timeout`->`systemd-run`), not the detached scope's `cbmc` child, so its
number is not the actual peak (confirmed: it reported ~29 MB on every run,
including ones where `ps` showed the real `cbmc` process well past 1 GB RSS).
Peak RSS below is read from polling `ps` on the live `cbmc` process instead;
none of the three runs came close to the 12 GB `MemoryMax` cap regardless of
which number is trusted — every run that stopped, stopped on the wall-clock
`timeout`, not the cgroup memory limit.

## Root cause: broader than IR-241's finding, and present before any call

IR-241 (and `verification/kani.rs`'s own module comment) attributed the
16 GB / 17 min CBMC blowup on the `evaluate` path to `Value` clones flowing
through `exact::Integer`'s `num_bigint::BigInt`, whose digit-vector
(`Vec<u32>`) representation forces every downstream comparison and
arithmetic step to go symbolic. That mechanism is real and reproduces here
too (both non-diagnostic runs show CBMC unwinding a `memcmp`-shaped intrinsic
loop, `<builtin-library-memcmp>`, past 4000+ iterations with no natural
bound).

But the third run shows the same non-terminating shape with **zero**
arithmetic and **zero** symbolic values: `ir286_package_check_and_drop_only`
only builds a one-function `PackageDeclarations`, calls `.check(...)`, and
drops the result. No `Frame::call`, no `Integer::add`, nothing symbolic at
all — and it still hits the identical unbounded `memcmp` unwind and times
out at 300 s.

The mechanism this points to: every `PackageDeclarations`/`CheckedPackage`
carries a `TypeEnvironment` (`src/exact/expression.rs`'s
`PackageDeclarations::types` field), and `TypeEnvironment` is two
`alloc::collections::BTreeMap` fields (`src/exact/composite.rs:867-868`),
present and dropped even when both are empty and no composite/enum/reference
type is ever declared by the package. Kani's model of `BTreeMap`'s generic
Drop/comparison machinery does not collapse to "trivially empty" the way a
concrete run would: with a small forced `--unwind 4`, the transcript instead
shows CBMC exploring dozens of distinct monomorphized
`alloc::collections::btree::node::*` functions (`NodeRef::
correct_childrens_parent_links`, `LazyLeafRange::init_front`,
`Handle::deallocating_end`, …) — real, load-bearing generic drop code for a
type this crate's runtime uses for real, not a harness artifact — and still
does not converge within 300 s.

So the finding is not "the arithmetic operator is expensive," it is: **the
function-application surface is unreachable by Kani today independent of
whether any value or arithmetic ever flows through it.** `PackageDeclarations
::check`, `CheckedPackage`, and `Frame::call` all sit behind a `TypeEnvironment`
whose `BTreeMap` fields alone are enough to defeat CBMC's unwinder inside a
300–900 s budget, before `Integer`/`BigInt` is even reached. Time, not
memory, is the resource that runs out — none of the three runs approached
the 12 GB cap.

## What was tried, and why nothing tractable was found

The ticket named three candidate fixes if the raw path proved intractable:
a bounded-i64 fast path, `#[cfg(kani)]` stubs for the bigint ops, or
`kani::unwind` bounds.

- **`kani::unwind` bound** — tried (`--unwind 4`, no source change). Did not
  help: it traded one non-terminating loop shape (`memcmp`) for another
  (BTreeMap's generic node-navigation functions), still timing out at 300 s
  with several GB of RSS and no verdict. A tighter bound would only report
  "unwinding assertion: FAILURE" faster, which is an honest signal of
  insufficient coverage, not a proof — not attempted further, since the
  ticket's own instruction is never to weaken the assertion, and reporting
  "FAILURE" instead of "TIMEOUT" would not be more informative here.
- **Bounded-i64 fast path** — not attempted. The diagnostic run
  (`ir286_package_check_and_drop_only`) shows the blowup precedes any
  arithmetic entirely, so a numeric fast path in `evaluate_integer_arithmetic`
  would not touch the actual bottleneck.
- **`#[cfg(kani)]` stubs for the bigint ops** — the one candidate that
  matches a real mechanism here, but the mechanism found is `TypeEnvironment`'s
  `BTreeMap`s, not (only) `Integer`'s `BigInt`. Stubbing either one under
  `cfg(kani)` means the harness would no longer hold the real
  `PackageDeclarations`/`CheckedPackage`/`TypeEnvironment` shape this crate
  actually ships — it would be proving a different program, not this one.
  That is a materially larger change than "prototype," is not sound with
  respect to what IR-286 asked to prove (the *real* function-application
  surface), and was not attempted.

No tractable and sound "smallest change" was found inside this spike's
budget. This reads as an architecture-level mismatch between CBMC's
model-checking approach and this crate's chosen `no_std + alloc`
representations (`BTreeMap`-backed `TypeEnvironment`, `BigInt`-backed
`Integer`), not a harness-tuning problem. Closing it for real would mean
giving `TypeEnvironment` and `Integer` Kani-friendly *production*
representations (e.g., small fixed-capacity sorted arrays in place of
`BTreeMap` for the package-declaration sizes this crate actually has, and an
i64/i128 fast path with bigint fallback for `Integer`) — a dedicated design
and implementation effort, sized well past a spike, and out of scope here.

## Recommendation

Do not add a Kani proof over `exact::expression`'s function-application
surface yet. QSL-22 scenario 1's generated harness would hit the same wall
this spike did. Either scope QSL-22 scenario 1 to the operator surface
`verification/kani.rs` already reaches (no `TypeEnvironment`, no `BigInt`),
or treat closing this gap as its own ticket against `TypeEnvironment`'s and
`Integer`'s production representations, not a Kani-side workaround.

## Finding 1: spike 1 blamed the wrong structures

Bisection shows `TypeEnvironment`'s `BTreeMap`s are **not** the cause. An
empty `TypeEnvironment` verifies in 0.7s, and they were never changed. Two
CBMC representation limits are the cause. Both involve a value that is
**read back from the heap** (a `Vec` or `Box`). The same values on the stack
verify at once.

1. **Niche-encoded discriminants.** `ValueType`'s tag lives in a niche of a
   payload `BigInt`'s `Vec` capacity. CBMC does not constant-fold that read
   from heap memory. So `drop_in_place::<ValueType>` explores the
   `Collection` arm, and `ValueType -> Box<CollectionType> -> ValueType`
   recurses without bound (more than 1100 levels in 300s). Spike 1's
   "BTreeMap node code" was this: with the recursion capped by
   `--default-unwind 3`, the garbage-discriminant paths walk into
   `QuantityUnit`'s `BTreeMap<NodeKey, Integer>` drop glue.
2. **Heap objects larger than 64 bytes.** CBMC tracks a heap object field
   by field only up to `--max-field-sensitivity-array-size` (64 by
   default). `ValueType`, `Value` and `FunctionDeclaration` are larger, so
   even an explicit tag is not folded.

Minimal local enums confirm both (`ir286_diag_m1`..`m8`):

## Where it stands

- **Solved:** building, checking and dropping a real package, and
  `check_expression`, all through the production types. Two changes did it:
  the explicit `ValueType` tag and the CBMC field-sensitivity flag.
- **Removed as blockers:** `BigInt` on the add path (inline `i64`
  `Integer`), `Value`'s niche tag, and `Meter::charge`'s consuming loop.
  Each one moved CBMC to the next hotspot.
- **Open, the next blocker:** running *any* `Body` through
  `CheckedPackage::evaluate` or `CheckedPackage::call` does not reach a
  verdict. That holds even with concrete input and an identity body. The
  controls rule out generic `Box<dyn Fn>` dispatch from a heap `Vec`. What
  is left is on the invocation path: the `Frame` / `RefCell<&mut Meter>`,
  `Outcome<Value>` / `Result<Value, Stop>` round-trips
  (`from_stop`/`into_stop`), `Value`'s manual iterative `Drop`
  (`drain_children`), and the `Evaluation` return. One of these hands CBMC
  a pointer or tag it cannot fold. The symptoms are an unfolded `Integer`
  tag on the direct call, and the root closure appearing as a dispatch
  target in `Frame::run`. Best estimate: the same class of fix (an explicit
  tag or a by-reference rewrite at one site), found by bisecting those
  pieces the way this note bisected `check`. About 2-4 more hours.

## Consequences outside RT

- CG: no source change. The generated oracle calls the same API, which is
  unchanged. A generated Kani harness running in a **CG** package also
  needs the same `[package.metadata.kani]` CBMC flag in *that* package's
  `Cargo.toml` (the flag is per package), or Kani's `--cbmc-args`.
- IR: none.
- Not measured: the package-wide flag's effect on the 8 `make kani`
  proofs' run times.

## Finding: every `Value` wrapped in another enum is expensive, and niches with padding lose tags

Kani encodes an enum as a tag plus a C union. Moving a `Value` into or
out of *any* enum (`Outcome`, `Result`, `Option`) becomes byte-level
union updates in CBMC. Their cost grows with the combined size of every
inline `Value` payload, and not linearly.

- A round trip `Outcome<T> -> Result<T, Stop> -> Outcome<T>` costs 0.12s
  of symex with `T = bool` and 0.67s with `T = Integer`, but 22s with
  `T = Value`.
- `Result<Value, u8>` wrap and unwrap: 13.3s. Plain by-value passes
  through two functions: 1.0s.
- A local model enum with `Value`'s real payload types takes 11.75s
  inline and 0.18s with the six large payloads boxed. With `Rational`
  and `Decimal` inline and the other four boxed, it takes 1.27s. With
  only one large payload inline, it takes 0.5-1.2s. No single payload is
  to blame; it is the combination.
- An explicit `#[repr(u8)]` tag on `Outcome` made the round trip *worse*
  (32.5s). Reverted.

A second shape loses tags outright. Kani writes `Ok(x)` into a
`Result<X, E>` as `{ nondet padding, x }` when the niche lives inside
`E`. The discriminant then comes back symbolic, and the `Err` arm is
explored under a symbolic guard. The merged return value makes later
drops walk `Value`'s manual `Drop` (`drain_children`) over garbage
collections without bound. The step trace
(`--show-goto-symex-steps`, first `[Guard size: N>1]`) found this in
`CheckedPackage::enter` (`Result<DepthGuard, Stop>`).

## The next blocker

In `call("f", [5])`, the `i64` payloads loaded for `lower <= value` in
`IntegerInterval::contains` (inside `validate_arguments`) are already
not constant. So the `Ordering` is symbolic from that point on. By the
time `f`'s body runs `integer_arithmetic_bits`, an `Integer` tag is
unfolded too, and `Integer::cmp` falls into the `BigInt` arm, whose digit
compare CBMC cannot bound. Every piece checked in isolation folds. So the
loss comes from the way the full call composes them, most likely
another niche-plus-padding `Result`/`Option` on the argument or
declaration path, like the two already fixed. Candidates, in order:
`plan_call`'s `Result<CallPlan, InputRefusal>` (`CallPlan` holds an
`Integer`, and `InputRefusal` holds a `String` whose capacity carries
the niche), `function()`'s `Option<&FunctionDeclaration>` from
`Iterator::find`, and `Frame::meter`'s `Result<Outcome<Integer>,
Refusal>`. The same step-trace method (the first `[Guard size: N>1]`
with a `Value`/`Integer` read under it) finds the site. Each fix so far
was 5-20 lines. Estimate: 2-3 more such sites to reach a verdict on the
concrete direct call, then symbolic add-one. 3-5 more hours.

# Spike 5: heap-stored enum payloads

Resume step 1 did not give 0: `guardscan.sh` on `diag3_plan_call_checked`

## Finding: an enum payload read back from the heap folds only if it covers the union with no padding

Kani encodes an enum as `struct { case, cases: union }` and builds a variant
by a byte update of a fresh (nondet) union. On the stack, CBMC reads a
member of that union back with the same offset and type, and folds it. A
`Box` or `Vec` is a byte array, so the heap copy and read are byte by byte.
Those bytes fold only when the union holds no nondet byte at all: the
variant must start at the union's offset 0 (no leading padding) and cover
the whole union.

| Harness (all on the heap) | guard>1 | Symex |
|---|---|---|
| `Vec<Integer>`, compared (no enum) | 0 | 0.19s |
| `Box<S3>` (`{i64, Option<Box<BigInt>>}`, no enum), `is_none` | 0 | 0.08s |
| `Box<Value::Integer>`, compared | timeout | - |
| `Vec<Value::Integer>`, compared | timeout | - |
| `Box<W1>`, `repr(u8) {A(bool), B(i64)}`: 7 bytes of leading padding | 192 | 0.06s |
| `Box<W9>`, `repr(u64) {A(bool), B(i64)}`: `B` covers the union | **0** | 0.12s |
| `Box<W10>`, `repr(u64) {A(bool), B(i64), C(i64,i64)}`: `B` is partial | 192 | 0.42s |
| `Vec<W11>`, `repr(u64) {A(bool), B(Integer), C(Box<i128>), D(u8,u64)}`: `Integer` covers the union | **0** | 0.30s |

Replacing the `Option<Box<BigInt>>` with an inline `BigInt` does not help:
num-bigint 0.4.8's `BigDigits` is itself an enum
(`Inline(Option<u64>) | Heap(Vec<u64>)`). A `Vec<BigInt>` (empty when small)
does not help either (`len` is in the same lost union bytes).

A sound global bound (`--default-unwind 3`, unwinding assertions on) makes
`diag3_plan_call_checked` verify (65s, 765 MB) but not the concrete direct
call (timeout 580s, 2.7 GB): once `big` is unknown, the `BigInt` arms of the
arithmetic are too large even when bounded.

So `Value::Integer` must cover `Value`'s union, and `Value`'s payload must
start at offset 0. That means a `u64` tag on `Value` and every other inline
payload at most 16 bytes (`size_of::<Integer>()`): `Rational` (32 bytes) and
`Decimal` (48) go behind a `Box`, as spike 3 did for `Quantity` and `Text`.

## The next blocker: `Outcome<Value>` cannot be covered by `Value`

The last unfolded read is the `Value` inside `Evaluation.outcome`. The
same rule holds on the stack for a nested enum:

| Harness (stack) | guard>1 |
|---|---|
| `W15 = repr(u64) {A(bool), B(W11)}`, `W11` (24 B) fills `W15`'s union | **0** |
| `W14 = repr(u64) {A(bool), B(W11), C(5 × i64)}`: `W11` does not fill it | timeout |
| `Outcome::Completed(Value::Integer(5))` (tag folds; the `Integer` inside does not) | timeout |

`Outcome<Value>`'s other payloads are `Incomplete` (40 B) and `Refusal`
(32 B, `CardinalityOutOfBound`), so `Value` (24 B) fills only part of the
union. There is no layout that satisfies both rules with today's public
types: `Value` would need to be at least 40 B, so `Integer` (which must fill
`Value`'s union for the heap argument reads) at least 32 B, and then
`Incomplete`, which holds an `Integer` inline, grows to 56 B. The only
exit is a public API change: `Outcome::Refused` and `Outcome::Incomplete`
holding their payloads behind a `Box` (both at most 24 B).

## Symbolic arithmetic: BigInt on branches CBMC cannot prune

A symbolic `x` makes every overflow and promotion test symbolic. CBMC
cannot prove `x + 1` does not overflow for `x` in `[0, 9]`, so it runs the
promoting branch too, and `num-bigint`'s loops there have value-dependent
bounds it cannot unroll. The fixes (commit `a02f0bd`, no API change):

- `add`, `sub`, `mul` and `neg` of unpromoted operands compute in `i128`,
  which cannot overflow, so they never reach `BigInt` arithmetic.
- `Integer::cmp` orders a promoted value against an unpromoted one by sign
  alone (the form is canonical, so a promoted value is outside `i64`).
- `magnitude_bits_integer` builds a small bit length without a range test.
- `Integer::from(i128)` promotes through four fixed 32-bit digits, not
  `BigUint::from(u128)`'s `while n != 0` loop.

| Harness | Verdict | Wall (CBMC) | Peak RSS |
|---|---|---|---|
| `diag5_symbolic_stack_add` (`evaluate_integer_arithmetic(x + 1)`, metered, symbolic `x`) | timeout 300s | - | 1.0 GB, then 0.6 GB after the fixes; still in `BigDigits::normalize`'s `rposition` |
| same, `--default-unwind 3` (unwinding assertions on) | **SUCCESS** | 59s (37s) | 552 MB |
| `diag5_symbolic_heap_add` (operand read from a heap `Vec<Value>`) | timeout 240s | - | 920 MB |
| `diag5_symbolic_evaluate_forget` (the full symbolic path, `Evaluation` forgotten) | timeout 580s | - | 1.4 GB |
| same, `--default-unwind 3` | timeout 580s | - | 2.8 GB |

The unwind bound is sound: CBMC checks that no path needs more iterations,

## What CG needs

For a generated Kani harness in a CG package to use this path:

1. The CBMC flag in *that* package's `Cargo.toml` (Kani reads it per
   package):
   ```toml
   [package.metadata.kani]
   unstable = { unstable-options = true }
   flags = { cbmc-args = ["--max-field-sensitivity-array-size", "1024"] }
   ```
   Or pass `-Z unstable-options --cbmc-args --max-field-sensitivity-array-size 1024`.
2. `ulimit -s unlimited` before `cargo kani`. Without it, CBMC segfaults
   (status 139) once expressions get deep. That is a crash, not a verdict.
3. For symbolic integer inputs, a sound unwind bound on the harness
   (`#[kani::unwind(3)]` or `--default-unwind 3`), with unwinding assertions
   left on. It must be at least 3 (`Meter::charge`).
4. No change to generated body code for today's API: the fixes are inside
   RT. A body should call `evaluate_integer_arithmetic` and `Frame::meter`
   as today.
5. Not enough yet: reading the result out of `Evaluation.outcome` does not
   fold (next section). A CG harness cannot assert on `f(x)` through this
   path until RT changes `Outcome`'s public shape. If RT boxes
   `Outcome::Refused`/`Outcome::Incomplete` payloads, generated code that
   builds or matches those two variants changes with it.
